# PACT — общий план MVP

## Идея

PACT — это слой делегирования полномочий для AI-агентов. Агент получает ограниченную миссию, предлагает конкретное действие, человек подтверждает именно это действие, а PACT повторно проверяет полномочия перед исполнением.

Главная демонстрация должна показать полный путь:

```text
рабочий контекст
  → разрешённая проекция данных
  → предложение агента
  → проверка PACT
  → подтверждение человека
  → повторная проверка
  → внешняя запись
  → подтверждённый результат
```

Ключевой сценарий после отзыва полномочий: старое предложение нельзя исполнить, даже если человек ранее видел его и нажимал подтверждение.

Формулировка продукта:

> PACT — a constitutional runtime for AI agents. Agents receive a mission, not unlimited authority.

## Цель хакатонного MVP

Собрать один работающий сценарий с:

- одним агентом;
- одним рабочим пространством Ambiguous;
- одним типом внешней записи — созданием задачи;
- ограниченным контрактом миссии;
- структурированными правилами конституции;
- обязательным human-in-the-loop;
- повторной проверкой полномочий перед dispatch;
- отзывом миссии;
- журналом решений и реальным результатом во внешней системе.

Полезное действие должно быть настоящим: PACT создаёт задачу в Ambiguous, получает реальный ID и может прочитать эту задачу после обновления страницы.

## Границы MVP

В основной сценарий входят OpenAI, CopilotKit и Ambiguous AI.

Auth0 подключается только после запуска основного пути и только если быстро доступна рабочая конфигурация. Он может защищать API PACT и проверять токен и scope, но не заменяет проверки конституции, контракта и подтверждения действия.

В этот MVP не входят Slack, Discord, Telegram, платежи, бронирование поездок, voice, shell, произвольный HTTP-инструмент и выполнение сгенерированного кода. Exa, Trigger.dev, OpenRouter и Cloud Run остаются возможными расширениями.

Готовый starter kit можно использовать как основу, но переименование starter не является функциональностью PACT. Новая часть должна быть видна в поведении системы: допустимое действие проходит, запрещённое блокируется до вызова адаптера, а изменение или отзыв полномочий делает старое разрешение недействительным.

## Прикладной сценарий

Рабочая среда содержит проект `Voice AI Pilot` и исходную задачу:

> Подготовить техническую демонстрацию голосового ассистента для клиента.

В задаче есть требования, срок, участники и внутренние заметки. Закрытые поля не должны попадать в контекст модели.

Пользователь поручает:

> Подготовь для Бакыта конкретную техническую задачу по этому пилоту. Работай только в текущем проекте. Не передавай модели закрытые поля. Перед созданием покажи мне результат.

Агент читает разрешённую проекцию исходной задачи, формирует содержательное follow-up предложение и показывает его пользователю. После подтверждения PACT создаёт задачу в том же проекте.

Идентификаторы проекта, пользователя и исходной задачи должны быть получены из подключённого workspace. Их нельзя придумывать или зашивать в код как универсальные значения.

## Constitution и Mission Contract

### Constitution

Конституция задаёт неизменяемые для агента ограничения. Для MVP достаточно фиксированного шаблона со структурированными правилами:

- агент не может менять собственные полномочия;
- запись разрешена только в выбранный проект;
- закрытые поля исходной записи исключаются до формирования контекста;
- внешняя запись требует подтверждения конкретного содержимого;
- отозванная или истёкшая миссия не допускает новых действий;
- запрещённые действия не передаются адаптеру исполнения.

Свободный текст можно показывать в интерфейсе, но источником истины должны быть поддерживаемые системой поля и проверки. Нельзя передавать текст конституции другой LLM и считать это enforcement-механизмом.

### Mission Contract

Контракт ограничивает конкретную миссию:

| Поле | Значение MVP |
| --- | --- |
| Mission | Подготовить follow-up для текущего клиентского пилота |
| Source context | Одна выбранная задача и её разрешённые поля |
| Workspace / project | Конкретные идентификаторы из Ambiguous |
| Allowed actions | Читать контекст, предложить задачу, создать задачу после подтверждения |
| Assignee | Бакыт после сопоставления с реальным ID |
| External write limit | Не более двух новых задач |
| Lifetime | Например, 10 минут для демонстрации |
| HITL | Перед каждой внешней записью |
| Mutation | Только через новое подтверждение контракта человеком |
| Revocation | Кнопка `Revoke mission` |

Если ограничение не перехватывается работающим серверным кодом, его нельзя включать в контракт. Неподдерживаемые ограничения должны отклоняться при создании контракта, а не тихо игнорироваться.

Конституция отвечает на вопрос «что агент никогда не может сделать». Контракт отвечает на вопрос «что разрешено этой миссии сейчас». Если агент предлагает запись в другом проекте, PACT должен вернуть понятное решение:

```text
Denied: project outside contract scope.
Outside mission scope. A new mission contract is required.
```

Версии конституции и контракта должны сохраняться. После изменения версии все неподтверждённые предложения аннулируются.

## Архитектура

Ответственности разделяются так:

1. Агент понимает рабочий контекст и предлагает структурированное действие.
2. PACT проверяет пользователя, миссию, версии правил, область проекта, исполнителя, срок, лимиты и состояние предложения.
3. Адаптер исполнения вызывает конкретный API Ambiguous и сохраняет внешний результат.

Модель может использовать строгий schema/function calling, но корректная структура аргументов сама по себе не даёт полномочий. Запрос на запись в чужой проект должен быть запрещён сервером.

Фактическая запись должна проходить только через контролируемый путь PACT. Не следует отдавать модели необёрнутые write-инструменты Ambiguous MCP.

Минимальные серверные сущности:

```text
ConstitutionVersion
MissionContract
ActionProposal
Approval
Execution
AuditEvent
```

Предложение действия должно включать как минимум:

```json
{
  "id": "proposal-id",
  "missionId": "mission-id",
  "constitutionVersion": 1,
  "contractVersion": 1,
  "action": "create_task",
  "arguments": {
    "projectId": "real-project-id",
    "assigneeId": "real-user-id",
    "title": "...",
    "description": "...",
    "dueDate": "..."
  },
  "status": "awaiting_approval",
  "expiresAt": "..."
}
```

Браузер передаёт при подтверждении только `proposalId`. Сервер достаёт сохранённые аргументы и не доверяет полям, повторно присланным клиентом.

Рекомендуемое состояние действия:

```text
proposed
  → awaiting_approval
  → approved
  → dispatching
  → sent
  → confirmed
```

Дополнительные состояния: `rejected`, `denied`, `expired`, `revoked`, `unknown_result`.

## Обязательные свойства исполнения

PACT должен обеспечить следующие инварианты:

- Если изменились аргументы, старое подтверждение неприменимо.
- Если миссия отозвана или истекла, подтверждение не запускает новое действие.
- Повторный клик по одному предложению не создаёт вторую задачу.
- При исчерпанном лимите новая запись блокируется.
- Действие за пределами проекта блокируется до вызова Ambiguous.
- Закрытые поля отсутствуют в отправленном модели контексте.
- Отзыв блокирует новые dispatch-запросы, но не обещает отменить запрос, который уже ушёл во внешнюю систему.
- Таймаут после отправки переводит действие в `unknown_result`. Его нельзя автоматически повторять без безопасной проверки идемпотентности.

Переход к исполнению и списание лимита должны быть атомарными относительно других действий той же миссии. Для двухчасового MVP достаточно одного локального сервера и последовательного исполнения.

## Human-in-the-loop

Пользователь должен подтверждать конкретное содержимое действия:

```text
Create task in Voice AI Pilot
Assignee: Bakyt
Due date: tomorrow
Content: [полное описание задачи]
Data destination: selected Ambiguous workspace
Mission capacity after execution: 1 task remaining
```

Кнопки: `Approve this action` и `Reject`.

Сервер при approval проверяет:

- действительность миссии и её срок;
- отсутствие отзыва;
- актуальность версий конституции и контракта;
- соответствие сохранённых аргументов контракту;
- доступ пользователя к выбранному проекту и исполнителю;
- оставшийся лимит внешних записей;
- состояние предложения и отсутствие предыдущего исполнения.

Auth0 machine-to-machine токен удостоверяет сервис. Он не доказывает, кто именно нажал кнопку в локальном демо. Если полноценная пользовательская аутентификация не готова, интерфейс следует описывать как работу доверенного оператора.

## Интерфейс

Одна рабочая страница должна содержать:

- слева — текущий проект и исходную задачу;
- в центре — предложение агента и карточку подтверждения;
- справа — панель PACT с версией конституции, активным контрактом, областью доступа, сроком, лимитами и `Revoke mission`;
- внизу — компактную историю событий.

Показывайте причину решения:

```text
Allowed: correct project, permitted assignee, active mission, one write available.
```

или:

```text
Denied: project outside contract scope.
```

Не используйте неопределённый `Trust score`. У этой цифры нет проверяемого смысла в рамках MVP.

Журнал в локальной базе — это audit trail для демонстрации. Его нельзя называть неизменяемым аудитом или защищённым от администратора журналом, если такие свойства отдельно не реализованы.

## Партнёрские интеграции

| Партнёр | Роль | Что показать |
| --- | --- | --- |
| OpenAI | Анализ разрешённого контекста и формирование предложения | Содержательная follow-up задача |
| CopilotKit | Контекст страницы, интерфейс агента и HITL | Агент работает внутри рабочего интерфейса |
| Ambiguous AI | Реальные рабочие записи | Созданная задача, ID и чтение результата |
| Auth0 | Опциональная защита API и проверка scope | Запрос без токена отклоняется |

Exa нужен только для публичного исследования, Trigger.dev — позднее для длительного ожидания подтверждения, OpenRouter — только после пересмотра ограничений маршрута данных, Cloud Run — только при уже готовом deployment. Mozilla не следует добавлять без конкретной необходимой функции.

## Что честно заявлять

Корректная гарантия MVP:

> В нашей демонстрационной интеграции все поддерживаемые внешние записи проходят через PACT; запрещённое действие не передаётся адаптеру исполнения.

Не следует заявлять, что PACT делает любого агента невзламываемым. Граница защиты — контролируемый серверный путь и его адаптеры. Компрометация сервера, зависимостей или появление нового незащищённого инструмента находится за пределами этой гарантии.

## Проверки перед демонстрацией

| Сценарий | Ожидаемый результат |
| --- | --- |
| Разрешённая задача и approval | Создана реальная задача, ID перечитывается |
| Пользователь отклонил предложение | Внешняя запись не создаётся |
| Проект вне контракта | Сервер отказывает до вызова адаптера |
| Аргументы изменены после показа | Старое подтверждение неприменимо |
| Миссия отозвана до исполнения | Старая карточка заблокирована |
| Повторное подтверждение | Вторая запись не создаётся |
| Лимит записей исчерпан | Следующая запись запрещена |
| Закрытое поле | Поле отсутствует в модели контекста |
| Контракт истёк | Новое действие не допускается |
| Таймаут внешнего API | Статус `unknown_result`, автоматического дубля нет |

Для негативных сценариев нужно проверять отсутствие вызова адаптера, а не только текст ошибки в интерфейсе.

## План на 120 минут

| Время | Результат |
| --- | --- |
| 0–15 мин | Starter запущен; тестовая задача создана и перечитана в Ambiguous |
| 15–40 мин | Контракт, серверные проверки scope, состояния и лимита |
| 40–65 мин | Сохранённое предложение, конкретный HITL, повторная проверка и отзыв |
| 65–85 мин | Сценарий клиентского пилота, PACT-панель, история и фильтрация контекста |
| 85–100 мин | Позитивные и негативные проверки; Auth0 только при готовом основном пути |
| 100–120 мин | Заморозка функциональности, видео, README и submission |

Если обычный Ambiguous workspace не запускается за первые 15 минут, можно рассмотреть временный sandbox с синтетическими задачами и отдельным адаптером. Это запасной путь с другими credentials, без MCP и с ограниченным сроком действия; его нужно явно обозначить в демо.

## Сценарий видео на две минуты

| Время | Сцена |
| --- | --- |
| 0:00–0:15 | Рабочий проект и проблема ограниченного доступа агента |
| 0:15–0:35 | Подтверждение контракта: проект, срок, действия |
| 0:35–1:05 | Агент готовит задачу; человек подтверждает; PACT создаёт запись и показывает реальный ID |
| 1:05–1:35 | Второе предложение; миссия отзывается; старое подтверждение блокируется |
| 1:35–1:50 | История: предложение → approval → dispatch → receipt |
| 1:50–2:00 | Роли партнёров и переносимость ядра на другие адаптеры и voice |

Финальная фраза:

> PACT separates policy, mission scope, human approval, and execution — and shows that revoked permission cannot authorize a new action.

## Дальнейшее развитие и VoxOS

PACT следует развивать как переиспользуемое ядро `policy/enforcement`, а не как вторую систему правил внутри VoxOS.

В ядре должны остаться конституция, контракт миссии, предложение действия, решение о допустимости, разрешение человека, состояние исполнения и результат. Ядро не должно зависеть от Slack-кнопок, React, синтеза речи или формата Ambiguous.

Адаптеры смогут позднее создавать CRM-записи, отправлять сообщения, переносить встречи или выполнять разрешённые действия в телефонии. Модель и канал могут меняться, а связь `permission → dispatch → receipt` должна сохраняться.

Для conversational agents важно отдельно учитывать, что распознанная речь не является разрешением, остановка TTS не отменяет внешнее действие, а согласие должно иметь чёткую область действия.
